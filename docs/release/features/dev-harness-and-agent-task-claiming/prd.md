# dev-harness-and-agent-task-claiming — PRD

## 背景

目前项目已经有三块零散的研发流程资产，但彼此没有串成一套可被「人 + 多个 AI agent」共同遵循的规范：

1. **文档范式**：`docs/README.md` 定义了 8 大模块 / features|bugs / 需求目录三级结构，以及 `prd.md` / `design.md` / `analysis.md` 等文件命名。
2. **需求注册中心**：`docs/requirements-registry.html` 提供「先对齐、后实现」的 6 环节看板（需求文档 → 设计文档 → 🔒 人工门禁 → 代码实现 → 测试用例 → 测试报告），并已支持从 `requirements-registry.data.js` 种子文件自动加载、卡片可跳转文档目录。
3. **建档 Skill**：`/add-feature-doc`、`/add-bug-doc` 能按范式落盘骨架。

**当前痛点**：

- 这套流程靠人脑记忆和口头约定，没有一份"权威总纲"把"文档怎么写 / 需求与 bug 怎么注册 / 流程门禁怎么走"讲清楚。
- 注册中心的状态存在浏览器 localStorage，**其他 agent 读不到**，无法把需求列表当作任务队列来认领、推进、回写进度。
- 没有定义"认领（claim）"语义：多个 agent 并行时，谁在做哪条、是否被占用、做到哪一步，全无记录，容易撞车或重复劳动。

## 目标

把上述零散资产整合成**一套标准化研发 harness**，使得：

1. 有一份**权威总纲文档**，规定文档怎么写、需求/bug 怎么注册、流程如何流转。
2. 需求/任务状态有一份**机器可读、git 可追踪的单一事实来源（SSOT）**，agent 与人都能读写。
3. 定义清晰的**任务认领协议**：其他 agent 能从需求列表里发现「可认领」的任务，认领后回写归属与进度，避免并发撞车。
4. 人在整套流程里**只承担「审核 / 通过门禁」**，其余（建档、注册、认领、实现、测试、回写）尽量自动化。
5. harness **可按项目偏好配置**：接入新项目时先问询用户偏好（如文档展示形态：HTML / Markdown / 两者都要），并把选择**自动写入项目规则**，后续建档/展示按规则执行，无需每次重复询问。

## 用户故事 / 使用场景

1. 作为项目负责人，我希望新人或新接入的 agent 读一份 `HARNESS.md` 就能完全理解该怎么提需求、怎么走流程。
2. 作为发起者，我说一句"做某需求"，agent 自动建档 + 注册到看板，我刷新就能看到，并能点进文档审核。
3. 作为审核者，我只做一件事：看完 prd/design 点「✓ 通过门禁」。
4. 作为执行 agent，我能扫描需求列表，挑一条「门禁已过、无人认领」的任务认领，做完回写状态为完成。
5. 作为第二个并行 agent，我能看到某条已被认领，于是跳过它去做别的，不重复劳动。
6. 作为新项目接入者，第一次启用 harness 时它先问我几个偏好（如"文档要 HTML / MD / 两者都要？"），我选完它把规则写好，以后建档都按我的选择来，不再反复问。

## 范围

### 包含

- 新增权威总纲文档 `docs/HARNESS.md`（流程总览 + 索引到 README / 注册中心 / skills）。
- 在注册中心种子 `requirements-registry.data.js` 的需求 schema 中新增认领相关字段（`status` / `assignee` / `claimedAt` 等，详见 design）。
- 升级 `requirements-registry.html`：展示认领状态徽章；合并逻辑支持从种子同步认领字段。
- 定义并文档化**任务认领协议**（状态机、字段语义、并发与门禁约束）。
- 新增一个 agent 用的 Skill（如 `/claim-requirement`），描述如何从需求列表认领与回写。
- **偏好问询与规则落盘**：harness 初始化时通过结构化问询收集用户偏好（首项为「文档展示形态：HTML / Markdown / 两者」），把结果写入项目规则的受管块（managed block），供后续建档与展示读取；偏好可重新问询、可手动改。

### 不包含

- 不做中心化服务端/数据库来托管任务队列（首版以 git 仓库内文件为 SSOT）。
- 不做实时多 agent 锁服务；并发冲突依赖 git 合并 + 认领前检查。
- 不强制改造历史需求文档；存量按需迁移。
- 不替换现有 8 大模块文档范式（沿用 `docs/README.md`）。
- 不实现自动 CI 触发 agent；认领仍由 agent 主动扫描发起。

## 验收标准

- [ ] 存在 `docs/HARNESS.md`，覆盖「文档怎么写 / 需求与 bug 怎么注册 / 任务如何认领 / 门禁如何流转」四块，并链接到 README、注册中心、相关 skills。
- [ ] 需求种子 schema 含认领字段，注册中心能展示「可认领 / 已认领(@谁) / 进行中 / 完成」状态徽章。
- [ ] 文档化的认领协议明确：哪种状态可被认领、认领需写哪些字段、门禁未过的任务不可进入实现类认领。
- [ ] 提供 `/claim-requirement` Skill，agent 按其说明可完成「发现→认领→回写」闭环。
- [ ] 人工只需审核与点门禁；建档、注册、认领、回写均由 agent 完成。
- [ ] 初始化时能问询「文档展示形态：HTML / Markdown / 两者」并把结果写入项目规则受管块；后续建档按规则执行（如选 HTML/两者则同步产出渲染版）。
- [ ] 偏好问询可重新触发，写入采用受管块标记，不破坏用户手写规则。
- [ ] 该需求自身通过本 harness 流程登记并展示在注册中心（自举/dogfooding）。

## 风险与未决事项（需在 design 决策）

- **门禁可见性**：人工"通过门禁"目前点在浏览器里、存 localStorage，**agent 读不到**。需决定如何把门禁审批结果落到 agent 可读的文件（见 design 的备选方案）。
- **SSOT 选型**：任务状态以 `requirements-registry.data.js`（JS 种子）为准，还是新建独立 JSON？两者与浏览器 localStorage 的合并/覆盖优先级需定义。
- **并发认领冲突**：纯文件 + git 下，两个 agent 同时认领同一条如何收敛。
- **assignee 标识**：agent 用什么 ID（模型名/会话 ID/自定义 handle）。
