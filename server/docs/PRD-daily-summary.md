# PRD：今日总结（Daily Brief）

> 版本: 1.0.0
> 最后更新: 2026-04-19
> 状态: 草案
> 关联 PRD: PRD-cross-device-memory-sync.md

---

## 一、背景与动机

### 1.1 现状

AgentMemory 已具备完整的「采集 → 压缩 → 存储 → 同步 → 展示」链路：

- 客户端 SDKAgent 把每次工具调用压缩为 Observation，会话结束生成 Summary
- 服务端 agent-mem-server 接收同步并提供按 `date / ide / project` 维度的聚合视图
- Web 时间线和 Markdown 导出都已经可以"按日期"看到一整天的事项

但**「日期维度」目前仍是一份冷冰冰的事件流**：用户看到的是 N 个会话、M 条观察、K 条总结的时间线，自己仍然要在脑子里二次整理"今天我到底做了什么、想了什么"。

### 1.2 痛点

1. **缺少叙事感**：当天的事项是分散的会话和操作，没有统一的叙事整理
2. **反馈感弱**：看完一天的列表，用户说不出"今天有什么收获"
3. **跨项目跳跃**：一天可能在 3 个项目里来回切换，缺少按项目梳理的视角
4. **想法未被沉淀**：用户对话中产生的思考、决策、犹豫没有被显式提炼出来
5. **客户端/服务端各看各的**：客户端只能看本机数据，跨设备整合需要专门的"今日回顾"

### 1.3 需求来源

来自 `server/docs/需求列表.md` 中的"体验需求"：

> 1. 添加日总结，增强反馈感

用户原话补充：

> 我希望加上一个维度是今日总结，就是可以基于今天的所有数据，让 agent 读取并总结对应内容，并展示今天使用者一天做了哪些事情，有哪些想法，等等，形成一个很好的对使用者的观察录，并反馈给使用者。

## 二、目标用户与角色

| 角色 | 描述 |
|:---|:---|
| 个人开发者 | 一天结束（或第二天早上）想要快速回顾"昨天我做了什么、有哪些想法"，作为工作反馈或写日报的素材 |
| 项目维护者 | 一天在多个项目间切换，想看"每个项目今天分别推进到了什么程度" |

---

## 三、用户场景

### 场景 1：晚间下班的"一日复盘"

> 小明 22:30 下班前打开 Desktop 的「今日总结」面板（或服务端 Web 页面），看到系统已经在 22:00 自动生成好今天的总结，按项目分组：
> - **agent-memory**：今天主要在调试同步链路，修了 4 个根本问题，整体反思是"幂等键设计前期没考虑全"。
> - **agent-mem-server**：跑通了 docker-compose 部署，配了一个 Token，发现读取接口未鉴权这件事得排进下周。
> 最后还有一段「整体回顾」：今天主要在围绕"跨设备同步"的可靠性打磨，下午三点后状态明显下降，后面那次重启服务花了 30 分钟才发现是端口没释放。

### 场景 2：第二天早上的"昨日续杯"

> 小明早上 9 点打开 Cursor，先在 Desktop 的「今日总结」面板把日期切到昨天。看到昨天列出的"未完成事项"和"明日建议"，直接知道今天该从哪里接着干。

### 场景 3：跨设备整合视角

> 小明上午用公司 Mac，下午回家用 Windows，晚上 Web 页面看到的「今日总结」是两台设备数据合并后的版本：
> - 上午在 mac-work 推进了 X
> - 下午在 win-home 完成了 Y
> - 整体上"今天算是把上午挖的坑都回填了"

### 场景 4：手动重新生成

> 小明 18:00 想提前看一下今天的总结。他在面板上点「立即生成」，前台显示生成中（约 20–60 秒），完成后立即看到一份基于截至 18:00 数据的总结。22:00 定时任务会再生成一次最终版覆盖。

### 场景 5：单机离线模式

> 小明的设备没配置远端服务器，但「今日总结」依然可用——客户端 SDKAgent 只读取本机数据生成本机版本，存在本地，Desktop 面板正常显示，无任何远端依赖。

## 四、功能性需求

### FR-1：今日总结生成（客户端 SDKAgent）

- **FR-1.1**：每台设备独立生成本设备本日总结，复用现有 SDKAgent（不引入新 LLM 配置）
- **FR-1.2**：输入数据范围：当日 00:00 至生成时刻 之间的所有 `sessions / observations / summaries`，仅本设备
- **FR-1.3**：输出结构：**按项目分组的多段总结 + 一段整体回顾**
  - 每个项目段：完成的事项、主要思考、遇到的问题、明日建议
  - 整体回顾：今天的总主题、情绪/状态观察、对使用者的"观察录"反馈
- **FR-1.4**：当日无任何数据时，跳过生成，不写入空总结
- **FR-1.5**：单次生成失败时记录错误，下次定时任务到时再尝试；不影响其他流程

### FR-2：触发机制

- **FR-2.1：定时自动生成**——每天 22:00（本地时区，可配置 `CODEBUDDY_MEM_DAILY_BRIEF_HOUR`）自动生成当日总结
- **FR-2.2：手动重新生成**——Desktop 面板和 Web 页面都提供「立即生成」按钮，覆盖当日已有总结
- **FR-2.3：补生成**——客户端启动时检查"昨日是否生成过"，若昨日仍有数据但无总结，则补生成一次（仅补昨天，不向前补更多）
- **FR-2.4：限流**——同一日期手动生成的最小间隔 60 秒，防止误点连击导致 LLM 重复消费

### FR-3：存储与同步

- **FR-3.1**：客户端新增 `daily_briefs` 表，保存每个 `(date, device_id)` 维度的一份总结
- **FR-3.2**：复用现有 SyncQueue 机制，把 `daily_briefs` 同步到服务端
- **FR-3.3**：服务端新增 `daily_briefs` 表，存储所有设备的每日总结
- **FR-3.4**：同一 `(date, device_id)` 的多次生成走 `INSERT OR REPLACE`（覆盖语义），不累积历史版本

### FR-4：服务端聚合视图

- **FR-4.1**：提供 `GET /api/v1/daily-brief?date=YYYY-MM-DD` 接口，**合并当日所有设备的总结**返回一份跨设备视图
- **FR-4.2**：跨设备合并策略：
  - 各设备按项目段直接拼接（标注来源设备）
  - "整体回顾"段：若仅一台设备有数据，直接采用；若多台设备都有，由服务端做一次轻量拼接（标题+各设备一段）
  - 不做服务端二次 LLM 调用（避免在服务端引入 API Key 依赖）
- **FR-4.3**：返回结构包含：日期、参与设备列表、按项目分组的段落数组、整体回顾段、生成时间戳

### FR-5：展示界面

- **FR-5.1：服务端 Web 页面**——在 `/web/` 现有时间线 Tab 旁新增「今日总结」Tab
  - 默认展示当日总结，提供日期选择器和「立即生成」按钮
  - 立即生成按钮调用客户端 Worker 接口（通过未来支持的远程触发，MVP 阶段仅展示已生成的版本，按钮文案改为「在客户端重新生成」）
- **FR-5.2：Desktop 客户端**——QuickPanel 新增「今日总结」面板（或在现有面板上新增 Tab）
  - 展示本机已生成的当日总结
  - 提供「立即生成」按钮，触发 Worker 的 `POST /api/daily-brief/generate`
  - 显示上次生成时间、生成状态（生成中 / 成功 / 失败）

### FR-6：本地查询接口（Worker）

- **FR-6.1**：`GET /api/daily-brief?date=YYYY-MM-DD` —— 读取本机当日总结
- **FR-6.2**：`POST /api/daily-brief/generate` —— 触发立即生成，body: `{ date?: 'YYYY-MM-DD' }`，默认今天
- **FR-6.3**：`GET /api/daily-brief/list?from=&to=` —— 列出区间内已生成的日期清单（供 Desktop 历史回看）

## 五、非功能性需求

### NFR-1：成本可控

- 单日 LLM 调用次数：1 次定时 + N 次手动（限流后通常 ≤ 3 次/天）
- 单次输入 Token 预算：上限按 `MAX_INPUT_OBSERVATIONS` 截断（默认 100 条），避免数据爆炸日的失控开销
- 当日实体数为 0 时**跳过 LLM 调用**

### NFR-2：隐私与合规

- 客户端生成，原始数据不出本机（与现有 SDKAgent 同等保护）
- 生成的成品总结才参与同步（与现有 Summary 同等策略）
- 提供 `CODEBUDDY_MEM_DAILY_BRIEF_ENABLED=false` 全局禁用开关

### NFR-3：性能与可用性

- 定时任务在后台异步执行，不阻塞 Hook 处理
- 单次生成耗时目标：≤ 60 秒（按现有 generateSummary 规模估算）
- 失败时不留下半成品记录（事务包裹写入）
- 服务端 `GET /api/v1/daily-brief` 响应 < 200ms（仅查表 + 内存合并）

### NFR-4：兼容性与零破坏

- 新增 `daily_briefs` 表通过 `EXPECTED_COLUMNS` / `IF NOT EXISTS` 自动建立
- 未启用此功能的旧客户端、旧服务端继续正常运行
- 同步队列对未知 kind=`daily_brief` 的旧服务端：客户端做一次能力探测，若服务端不支持则跳过该 kind 的同步并告警一次

## 六、MVP 范围（Phase 1）

### 包含

- 客户端 `daily_briefs` 表 + 生成器 `DailyBriefGenerator`
- 定时任务（22:00 + 启动时补昨日）
- Worker 三个接口：查询 / 触发生成 / 列出区间
- SyncQueue 增加 `daily_brief` 类型
- 服务端 `daily_briefs` 表 + 同步接收 `POST /api/v1/sync/daily-briefs`
- 服务端聚合 `GET /api/v1/daily-brief?date=`（多设备合并）
- 服务端 Web 页面新增「今日总结」Tab（只读 + 日期切换）
- Desktop QuickPanel 新增「今日总结」入口（只读 + 立即生成按钮）

### 不包含（后续阶段）

- 周总结 / 月总结
- 服务端 LLM（不引入服务端 API Key 依赖）
- 跨用户、团队总结
- 总结的多版本历史保留（当前直接覆盖）
- 服务端 → 客户端的"远程触发生成"
- 总结结果的二次编辑 / 收藏 / 标签

## 七、成功指标

| 指标 | 目标 |
|:---|:---|
| 自动生成成功率 | ≥ 95%（定时任务 7 天滚动统计） |
| 平均生成耗时 | < 45 秒 |
| 首屏可用率 | 22:30 后打开页面，当日总结可见率 ≥ 90%（在当日有数据的前提下） |
| 跨设备合并正确性 | 多设备日期一致时，Web 页面能看到所有设备的项目段，无遗漏 |
| 用户感知 | 内部试用一周后，自评"今日反馈感"问卷分数 ≥ 4/5 |

## 八、待确认问题

1. **时区**：定时任务使用客户端本地时区（每台设备各自的 22:00），跨时区合并时按 `date_local`（YYYY-MM-DD 字符串）对齐，是否接受？
2. **失败展示**：单设备生成失败时，跨设备聚合视图是否要显式展示「设备 X 当日总结生成失败」？MVP 倾向于展示一行简短状态。
3. **空白日处理**：周末/请假当天可能完全无数据，是否要生成一份"今日休息"占位总结？MVP 倾向于不生成。
